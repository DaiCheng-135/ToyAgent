# 子代理：一个骗了我很久的名字 —— spawn 到底是开线程还是开进程？

> **学习札记 · ToyAgent Step13**
> 配套代码：[`SubagentAgent.java`](./SubagentAgent.java)
> 阅读前提：知道 `Agent` 接口只有 `chat(String)` 一个方法，知道「工具调用 = 模型吐 JSON、代码执行、结果塞回去」这个循环。

---

## 缘起

代码里两个词把我唬住了：**`spawn`** 和 **`fork`**。

`spawn` 让我想到开进程，`fork` 让我想到 `fork()` 系统调用。我下意识以为这一步在讲**并发** —— 主代理把活儿甩出去，子代理在旁边跑，跑完了合回来。

结果把 151 行看完，我愣住了：

> **没有线程，没有进程，没有并发。**
> 就是同一根线程上，又拼了一组 `messages`，再调了一次 `model.chat()`。

那它凭什么叫「子代理」？它到底「独立」在哪？

这篇就是回答这一个问题。**重点在第三节** —— 为什么这个设计值得存在。

---

## 一、先破误解：「派遣」的全部技术内容，是 10 行代码

先看 `dispatch()` 到底干了啥（`SubagentAgent.java:110-131`），去掉错误处理，骨架就这些：

```java
List<Message> childMessages = new ArrayList<>();
childMessages.add(Message.system(子代理的提示词));   // ① 拼一组新消息
childMessages.add(Message.user(task));
String report = model.chat(childMessages).trim();     // ② 再问模型一次
return report;                                        // ③ 返回一个字符串
```

**没有任何魔法。所谓「派遣子代理」，就是「另起一组对话，问模型一句话」。**

- 不是新进程 —— 它在主代理的同一个 JVM、同一根线程里
- 不是新线程 —— 它同步执行，跑完了才轮到主代理继续
- 也不是什么「独立的智能体实例」—— 它就是一次普通的 `model.chat()`

那它「独立」在哪？

> **独立在上下文（context），不独立在进程。**

---

## 二、子代理唯一的产出：一个字符串

子代理跑完，`dispatch()` 返回的是 `report` —— 一个 `String`。

主代理这边，只收到这一行（`SubagentAgent.java:97`）：

```java
messages.add(Message.user("子代理 " + name + "(" + mode + ") 执行结果: " + result));
```

**这就是整个机制的核心约定：**

> **子代理的中间过程，主会话一个字都看不见。只有最终结论进主会话。**

子代理内部问了几轮、试了几次、翻了哪些东西 —— 全部留在它自己那组 `childMessages` 里，随风而去。主代理手里只剩一个字符串。

这个「只见结论、不见过程」，就是「子代理」三个字的全部含义。

---

## 三、为什么「隔离上下文」是刚需（这才是子代理存在的理由）

**主代理的上下文是稀缺资源。** 它有限、每轮都要重发、还按 token 收钱。

想象没有子代理的一天：

```
用户：帮我调研一下 Agent 协议的趋势

主代理：调搜索 ×10 次   ← 10 坨搜索结果全进主会话
        读文件 ×8 个     ← 8 坨原文全进主会话
        试错 ×3 轮       ← 3 坨废稿全进主会话
        ……主会话被垃圾撑爆了
```

有了子代理：

```
用户：帮我调研一下 Agent 协议的趋势

主代理：dispatch_subagent(name=researcher, task="调研 Agent 协议趋势")
        ↓ 子代理在自己的上下文里翻江倒海
        ↓ 吐回来：3 条要点结论
主代理：（手里很干净，只有 3 条要点）
```

一句话：

> **子代理不是让主代理「多干活」，是让它「少记垃圾」。**
> **结论比过程值钱。**

顺带两个白拿的好处：

| 好处 | 说明 |
|---|---|
| **专业分工** | `researcher` / `writer` 各有各的人格（系统提示词），互不污染 |
| **可递归** | 子代理用的还是 `model.chat()` —— 同一套。理论上子代理还能再派子代理（分形） |

## 四、spawn vs fork：差别就是一行 `if`

代码里就这一处（`SubagentAgent.java:119-123`）：

```java
if (fork) {
    sys.append("\n【继承的父会话上下文】\n").append(String.join("\n", parentTranscript));
} else {
    sys.append("\n（spawn 模式：全新实例，看不到父会话）");
}
```

| | **spawn** | **fork** |
|---|---|---|
| 上下文 | 全新，0 条历史 | 继承父会话 |
| 类比 | 叫个外包，只给任务书 | 叫同事过来接着聊 |
| 适合 | 无状态专项任务 | 「接着刚才的话题继续做」 |
| 怎么触发 | `mode: "spawn"` | `mode: "fork"` |

接口注释里给的教学例子，正好对照（`SubagentAgent.java:28-31`）：

```text
记住：我最喜欢紫色
fork 一个子代理，让它写一句贺词    —— 子代理继承父会话，贺词里带紫色 ✅
再 spawn 一个子代理写贺词          —— 全新实例，贺词里没有紫色 ❌
```

同一个子代理、同一个任务，**只因为 `mode` 不同，一个知道「紫色」，一个不知道。**

### 4.1 一个容易忽略的细节：fork 拿的是**快照**，不是引用

```java
String.join("\n", parentTranscript)
```

**这个 `String.join` 的动作，就是「快照」发生的时刻。**

它把 `List` 拼成了一个**新字符串**。所以：

- fork 出去的子代理，拿到的是一份**拷贝**
- 之后父会话再怎么追加，子代理**毫不知情**

假如这里传的是 `parentTranscript` 这个 `List` **引用**，父会话一边追加、子代理一边读，那就乱套了。

> **不是「隔离了才隔离」，是「拷贝了才隔离」。**

## 五、和 Step12 多智能体，到底差在哪？

这是最容易混的一对，我把它们摆一起：

| | **Step12 多智能体** | **Step13 子代理** |
|---|---|---|
| 谁决定角色 | **程序员**（写死在代码里） | **模型**（运行时输出 JSON 决定） |
| 流程 | 固定流水线：规划 → 研究 → 写作 → 审查 | 动态：要不要派、派谁、派几个，模型说了算 |
| 代码长相 | 4 个 `model.chat()` 挨着写死 | 一个循环 + 一个 `dispatch()` |
| 加一个新角色 | 改代码、重新部署 | 改一行 `CHILDREN`，模型下次自动「看见」 |
| 类比 | **流水线工厂** | **派活给同事** |

Step12 的 `chat()` 里是这么写的（`MultiAgent.java:43-69`）—— 四个角色**硬编码**挨着排：

```java
String planRaw = model.chat(...);    // 规划者
String notes   = model.chat(...);    // 研究员
String draft   = model.chat(...);    // 写手
String review  = model.chat(...);    // 审查员
```

而 Step13 只有一个 `for` 循环，派不派、派谁，**由模型吐的 JSON 决定**。

一句话：

> **Step12 是「流程图写死」，Step13 是「模型现场决定」。**

这也正是为什么 Step13 对应 **Claude Code 的 Task 工具** —— 主代理自己判断该不该派、派谁。

## 跑一遍：把「叫同事帮忙」走完全程

### 先把这个比喻立起来

| 代码里 | 现实里 |
|---|---|
| 主代理 | **你自己** |
| 子代理 | **被你叫来帮忙的同事** |
| `parentTranscript` | **你俩的共同聊天记录**（记着之前聊过啥） |
| `dispatch(name, mode, task)` | 走到同事工位，说「帮我看下这个」 |
| `mode = "fork"` | **一直跟你开会的同事** —— 知道前面聊了啥 |
| `mode = "spawn"` | **新来的同事** —— 只知道你此刻给他的任务 |
| `report`（一个字符串） | 同事给你的**一句话答复** —— 他查了什么、试了什么，**你看不见** |

**关键在最后一行**：同事干活的**过程**不进你的聊天记录，只有**结论**回来。

### 走一遍

**第 1 次对话：`"记住：我最喜欢紫色"`**

```java
parentTranscript = [ "用户: 记住：我最喜欢紫色" ]
// 主代理回答后（SubagentAgent.java:103）
parentTranscript = [ "用户: 记住：我最喜欢紫色",
                     "助手: 好的，记住了！" ]
```

**第 2 次对话：`"fork 一个子代理，让它写一句贺词"`**

`chat()` 先把你这句话记上（`SubagentAgent.java:71`）：

```java
parentTranscript = [ ..., "用户: fork 一个子代理，让它写一句贺词" ]
```

模型吐 JSON，决定派遣（`SubagentAgent.java:85-90`）：

```json
{"tool": "dispatch_subagent", "name": "writer", "mode": "fork", "task": "写一句贺词"}
```

进 `dispatch()`，**子代理拿到的那组 messages**（`SubagentAgent.java:117-125`）：

```java
[ system("【子代理身份】你是写作子代理。根据任务输出一段 50 字以内的短文，不解释。
          【继承的父会话上下文】
          用户: 记住：我最喜欢紫色
          助手: 好的，记住了！"),
  user("写一句贺词") ]
// 返回 report（假设）："愿你新岁尽欢愉，紫色是你心头的浪漫。"
```

**子代理看得见「紫色」** —— 因为 fork 把父会话拼进去了。

回填主会话（`SubagentAgent.java:96-97`）：

```java
messages.add(Message.assistant(raw));
messages.add(Message.user("子代理 writer(fork) 执行结果: " + report));
// 主代理据此作答，并写回 parentTranscript
parentTranscript = [ ..., "助手: 愿你新岁尽欢愉……" ]
```

**第 3 次对话：`"spawn 一个子代理写贺词"`**

同样派遣，但 `dispatch()` 走的是 else 分支（`SubagentAgent.java:121-123`）：

```java
[ system("【子代理身份】你是写作子代理...
          （spawn 模式：全新实例，看不到父会话）"),
  user("写一句贺词") ]
// 返回 report（假设）："祝你万事顺遂，前程似锦。"
```

**没有「紫色」了** —— 因为 spawn 的同事没参加过之前的会。

### 一眼看穿 fork 和 spawn

| | fork 的同事 | spawn 的同事 |
|---|---|---|
| 知不知道「你喜欢紫色」 | ✅ 知道 | ❌ 不知道 |
| 代码差别 | `String.join(parentTranscript)` 拼进了 system（`SubagentAgent.java:120`） | 只写一句「看不到父会话」（`SubagentAgent.java:122`） |

**一行 `if` 的距离。**

## 落脚：回到这份代码

151 行，拆成三块就清楚了：

```text
chat()      主代理：拼 messages（含父会话上下文）→ 循环问模型
             模型说 {"tool":"dispatch_subagent", ...} → 调 dispatch()
dispatch()  子代理：拼一组全新 messages → model.chat() → 返回一个字符串
CHILDREN    子代理档案：名字 → 职责提示词
```

几个具体锚点：

| 位置 | 是什么 |
|---|---|
| `SubagentAgent.java:50` | `CHILDREN` —— 子代理的「档案柜」。**加子代理 = 往这个 Map 加一行** |
| `SubagentAgent.java:56` | `parentTranscript` —— 父会话上下文，**就是个 `List<String>`** |
| `SubagentAgent.java:76-78` | 每轮把整个 `parentTranscript` 拼进 system prompt —— 「主代理记得聊过啥」的全部实现 |
| `SubagentAgent.java:117-127` | `dispatch()` 全体。**子代理的「派遣」，就是这 10 行** |
| `SubagentAgent.java:127` | 子代理跑完，只返回 `report` 一个字符串 |

注意这里**没有**任何「并发」「隔离的技术手段」「沙箱」——

所谓「会话记忆」是**几行字符串**；
所谓「派遣」是**再调一次 `model.chat()`**；
所谓「独立上下文」是**没把父会话拼进去**。

**读这个文件的价值，不是学「怎么做多代理」，而是看清一个思想：**

> **「子代理」是个「上下文」概念，不是「进程」概念。**

---

## 一句话收束

> **子代理不是「跑在别处的另一个智能体」。**
> **它是「另起一组对话，问模型一句话，只把答案拿回来」。**
> 它全部的「独立性」，都在**上下文隔离**这四个字上。

配套对照：

| 问题 | 答案 |
|---|---|
| 是进程 / 线程吗？ | **都不是。** 同进程、同线程、顺序执行 |
| 那「派遣」是什么？ | **再拼一组 `messages`，再调一次 `model.chat()`** |
| spawn / fork 差在哪？ | **要不要把父会话上下文拼进子代理的 system prompt** |
| 子代理产出什么？ | **一个字符串**。中间过程主会话看不见 |
| 为什么需要它？ | **让主代理少记垃圾** —— 结论比过程值钱 |
